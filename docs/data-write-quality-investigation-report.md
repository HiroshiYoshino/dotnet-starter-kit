## 1. 先に押さえたい結論

**このアプリには、データを安全に保存するための部品はあるものの、一つの機能を最初から最後まで安全に完了させる保証には、まだつながっていない箇所があります。**

例えば、一回のDB保存をまとめて確定する仕組み、同じ行を重複して作らせない制約、失敗したイベントを送り直す仕組みはあります。しかし、それだけでは「異なる二件の入金が両方残高へ反映される」「登録したユーザーに必要な初期権限がそろう」「削除に失敗したファイルを後から再処理できる」とは限りません。

特に重要な論点は、次の五つです。

| 論点 | 具体的に何が問題か | なぜ優先して考えるか |
|---|---|---|
| 正しい値を書いているか | 前月の請求用データに現在月の利用量を保存する経路がある。 | 保存も再実行も成功するのに、業務上の値が間違う。 |
| 同時実行で更新が消えないか | 残高・在庫・契約期限を読み取って加算する処理で、別々の変更の片方が上書きされ得る。 | 個々の操作は成功しても、最終値が操作の合計にならない。 |
| 途中停止後に残りを起動できるか | 業務データ保存と、イベント保存・ジョブ登録が別になっている。 | データだけできて、必要な後続処理が永久に始まらない状態があり得る。 |
| 再実行で二重反映しないか | 処理済み記録が業務保存の後に書かれる、または再実行を新しい操作として扱う。 | リトライを増やすほど、通知・外部送信・加算が重複する場合がある。 |
| 失敗後も復旧の材料が残るか | 外部ファイルの削除失敗時に復旧用の作業記録を残さず、DB側の対象行を消す経路がある。 | 後で処理し直そうとしても、対象の保存先などを追えなくなる。 |

一方、すべての機能へ大きなトランザクションやOutboxを追加するのも適切ではありません。単一の状態保存で目的を満たす機能、表示用の通知を後から再取得できる機能、金額や不可逆な削除を扱う機能では、必要な保証が違います。

今回の重点テストは**46件すべて成功**しました。ただし、これらは主に共通基盤の既存テストです。以下で説明する業務上の競合や途中停止を、実際のPostgreSQL・Redis・外部ストレージで再現したわけではなく、指摘した課題が解消されたという意味ではありません。

## 2. 調査範囲と、どこまで確認できたか

対象は、Identity、Billing、Multitenancy、Catalog、Tickets、Chat、Files、Webhooks、Notifications、Auditingの10モジュールです。APIからの同期書き込みだけでなく、内部サービス、イベント受信処理、バックグラウンドジョブ、清掃処理も対象にしています。

静的な探索で102件のコマンドハンドラーを確認し、追加のサービスやジョブなどと合わせて39の機能グループに整理しました。そのうち33グループは代表的な処理経路を詳しく読み、6グループは存在と分類の確認にとどめています。**33グループに含まれるすべての派生操作を、同じ深さで検証したわけではありません。**

実装の調査基準はコミット`a967537526f3b769c7d268da3ed2a6920af65ce9`です。本文のソースリンクもこの時点に固定しています。一方、重点テストは、そのHEADに利用者が行ったNuGet依存更新を加えた作業ツリーで実行しました。元コミットそのままの依存構成で成功したとは扱いません。

### 事実・分析・提案を分けて読む

本書の「起こり得る」は、保存の順番や条件分岐から導いた反例です。実際の障害注入で再現済みという意味ではありません。また、「必要」とする保証の一部は、業務側の確認を要する仮説です。

| 記述の種類 | 本書での意味 |
|---|---|
| 実装から確認したこと | 保存順序、制約、条件分岐、例外処理、既定設定など、ソースに根拠がある事実。 |
| 業務要件の確認が必要なこと | 「通知は必ず届くべき」「既読は後退させない」など、採用するかを確認すべき条件。 |
| ソースから考えられる失敗例 | どの時点で止まると何が残るか、並行実行で何が起きるかという分析。 |
| テストで確認したこと | 実際に選択して実行した46件の対象と条件。全機能の保証へは拡張しない。 |
| 見直し方向 | 必要保証を満たすための方式候補。実装済み・承認済みではない。 |

本番のインスタンス数、実効設定、専用DBの利用範囲、バックアップや復元手順、監視の担当者・対応期限は未確認です。初期化・シード・起動時権限同期、CLI、フロントエンドの再送方針も詳細評価の対象外です。

## 3. 判断に必要な言葉と考え方

### 「保存できた」と「機能が完了した」は違う

ユーザー登録を例にすると、「ユーザー行ができた」「初期権限が付いた」「確認メールの送信が受理された」「メールが届いた」は別の状態です。どこまでそろえば登録成功とするかによって、まとめて保存すべき範囲や、途中失敗後の回復方法が変わります。

本調査では、主に四つの性質を見ています。

| 性質 | 日常的な言い方 | 確認したい例 |
|---|---|---|
| 正確性 | 書いた値が正しい。 | 請求対象月、通貨、数量、丸め方が合っているか。 |
| 安全性 | 間違った状態を作らない。 | 二重入金、更新の取りこぼし、権限の中途半端な置換がないか。 |
| 完了性 | 受け付けた仕事が放置されない。 | 再起動後も未完了を見つけ、完了か要対応へ進めるか。 |
| 結果の確認可能性 | 今どうなったか分かる。 | 未実行、処理中、成功、失敗、結果不明を区別できるか。 |

本文では、次の用語も使います。

| 用語 | 本書での意味 |
|---|---|
| 正本 | 正しい状態を判断するときの基準となるデータ。例えば、表示用キャッシュと区別したDBの業務記録。 |
| 保存境界・原子性 | 複数の変更を「全部確定するか、全部確定しないか」の単位にすること。 |
| 版管理・競合検査 | 読み取った後に誰かが更新していないか、版番号などで検査すること。文書の履歴管理とは異なる。 |
| best-effort | できる範囲で実行するが、失敗時の必達や回復までは約束しない方式。 |

### 再実行できることと、安全に再実行できることは違う

**冪等性**とは、同じ論理操作を繰り返しても効果が増えない性質です。在庫を「10に設定する」と「10増やす」では、再実行の意味が違います。後者には、同じ調整を二回適用しないための操作識別が必要になります。

さらに、同じ操作の重複防止と、異なる操作の取りこぼし防止も別です。同一の入金を一回に抑える制約があっても、別々の入金が同時に同じ残高を読んで上書きすれば、片方の増額が失われます。

### リトライ、再開、補償、訂正は使い分ける

一時的な接続障害なら、同じ処理を再試行する**リトライ**が有効です。途中まで成功した長い処理では、完了済みの段階を飛ばして残りを進める**再開**が必要です。外部ファイルを作った後でDB保存に失敗した場合などは、後から不要物を片付ける**補償**が必要になることがあります。誤った請求などでは、事実を消すのではなく履歴を残して直す**訂正**が適切な場合があります。

特に注意すべきなのは、**結果不明**です。外部への送信がタイムアウトした場合、相手が処理していないとは限りません。成功して応答だけ失われた可能性があるため、単純な再送ではなく、操作IDによる重複排除や結果照会が必要です。

### 評価は「部品の有無」ではなく「必要保証との差」で決める

本書の「優先見直し」は、想定する必要保証に対し、重要な反例経路が見つかっている状態です。「改善推奨」は、競合時の扱いや復旧性を改善したい状態です。「仕様次第」は、欠損・上書き・遅延などを許容するかで結論が変わります。「概ね妥当」も、読んだ代表経路と前提条件に限った評価であり、モジュール全体のお墨付きではありません。

詳細版では15観点に分けていますが、本書では文章の中で次のようにまとめて扱います。

| 読むときのまとまり | 含めている観点 |
|---|---|
| 正しいデータになるか | 正本と計算の正確性、入力値・精度・単位、業務上の一意性や参照関係。 |
| 書き込みが食い違わないか | 一緒に確定すべき更新、同時更新、同じ操作の重複、古い要求やイベントの順序。 |
| 障害後も先へ進めるか | 再試行、起動要求と進捗の保存、再起動後の発見、外部効果と補償。 |
| 後から照合・訂正できるか | キャッシュやカウンタの収束、操作の追跡、監査、保持・削除。 |
| 実際の構成で運用できるか | テナントとDBの分離、複数インスタンス、検出・通知・復旧責任。 |

## 4. 共通基盤は何を守り、何を守らないか

### DBトランザクション: 一回の保存は守るが、その前後まで自動では守らない

関係DBに対する一回の`SaveChangesAsync`では、その保存内の更新をまとめて確定できます。ただし、その前に読んだ値、別の保存呼び出し、別のDB、Redis、ファイル、HTTP送信まで自動で一体化されるわけではありません。

Outboxには、同じ接続上のトランザクションに参加する仕組みがあります。しかし、呼び出し元が業務保存とOutbox保存を囲むトランザクションを開始していなければ、二つの保存は独立したままです。また、共通のPostgreSQL設定ではDB障害時の自動実行再試行を有効化しておらず、実行戦略を呼ぶコードがあるだけでは再試行が有効とは言えません。

根拠: [DB provider設定][db-provider]、[Outboxのトランザクション参加][outbox-enlist]。

### APIの重複防止: 同じ応答を返せるが、業務効果の一回性とは同じではない

一部のAPIでは、同じキーの要求に保存済みの成功応答を返せます。適用にはエンドポイント側のフィルター設定と要求ヘッダーが必要で、全ハンドラーに一律適用されるわけではありません。既定では応答を24時間保持し、実行中の予約は1分です。

しかし、業務保存の後、応答をキャッシュする前に停止すれば、再送時に業務処理がもう一度動く可能性があります。処理が予約期限を超えた場合、キャッシュが使えない場合、保持期限後の再送も別に考える必要があります。同じキーで異なる入力を送った場合の本文照合も確認できていません。

これは便利な再送対策ですが、金額や在庫の「同じ操作を一回だけ反映する」保証の代わりにはなりません。根拠: [冪等性フィルター][idempotency]。

### Outbox: 保存済みイベントは送り直せるが、保存されなかったイベントは救えない

Outboxは、後で送るイベントをDBに保存し、配送担当が取り出して送る仕組みです。保存済みのイベントについては、失敗時の待機・再試行や、試行上限後の隔離状態があります。

既定の連続失敗では、初回を含む5回の失敗でdead-letterになります。「何度でも必ず完了する」仕組みではありません。業務保存だけ成功してイベント保存に到達しなかった場合は、配送リトライの対象自体がありません。再投入のための内部APIがあっても、運用者が何を見ていつ対応するかは別に決める必要があります。

また、担当権の期限が切れた後も古い処理担当が動き続ける場合の、所有者確認や古い担当の確定拒否は確認できていません。配送側だけでなく受信側も重複に備える必要があります。根拠: [Outbox設定][event-options]、[配送処理][outbox-dispatch]、[取得と状態更新][outbox-claim]。

### Inbox: 処理済み記録はあるが、効果と記録の間に隙間がある

Inboxは「このイベントをこの受信処理で処理済みか」を記録します。現在は受信処理が完了した後に記録するため、業務保存だけ成功して記録前に停止すると、再配送で同じ効果が生じ得ます。

加えて、処理済み記録の保存では、すべての`DbUpdateException`を重複登録のように扱って抑制しています。実際の重複制約違反かどうかを区別しないため、別の保存エラーまで正常終了に見える可能性があります。

Inboxの存在だけで「一回だけ処理できる」とは判断できません。根拠: [イベント受信の順序][event-bus]、[Inbox保存][inbox-store]。

### ジョブとドメインイベント: 「呼び出した」だけでは耐久的な起動にならない

Hangfireは、登録済みのジョブを永続ストレージに持てます。ただし、業務データを保存してからジョブを登録するまでの間に停止すれば、ジョブは残りません。

また、ローカルのドメインイベントは、DB保存の後にメモリ上のイベントを公開する処理であり、耐久キューではありません。明示的な外側のトランザクションがある場合は、その最終コミット前に公開される場合もあります。「ドメインイベント経由だから業務変更と同時確定する」とは言えません。

根拠: [ジョブ基盤の登録][jobs-config]、[ドメインイベントの発行][domain-events]。

### テナント分離: 正しい行条件と、正しいDB接続は別に確認する

共有DBでテナントIDを絞ることと、専用DBを持つテナントの接続先を選ぶことは別の問題です。

Outboxを読み出す側は接続文字列を含むテナント情報を設定しています。一方、イベント受信側ではテナントIDだけを設定する経路があり、受信処理のDB接続が既定接続へ戻る可能性があります。正しいOutboxから読めたからといって、正しいDBへ業務効果を書いたとは限りません。

これは専用DB構成で優先して実測すべき事項です。共有DBでも同じ不具合になると断定したり、横断データを扱うBillingへ無条件に一般化したりはしません。根拠: [読み出し側のスコープ][drain-scope]、[受信側のスコープ][tenant-scope]、[DB接続の選択][base-db]。

## 5. 機能別の結果と見直し方向

以下の評価は、詳細版の代表経路に対する評価を引き継いでいます。見直し案は方式候補であり、実装を変更したという意味ではありません。

機能を横断して対応を考える場合は、[第6章の課題・修正パターンの類型](#remediation-types)と[修正作業の切り分け](#remediation-work-units)を参照してください。同じ原因を持つ機能をまとめて見渡せますが、一つの機能が複数の対策を必要とする場合もあります。

### 5.1 ユーザー・認証・権限（Identity）

#### ユーザー登録 — 優先見直し

ユーザー作成、ロール付与、グループ保存、確認メールのジョブ登録、イベント保存が段階的に行われます。また、同じ登録を表す統合イベントが、登録サービスとドメインイベント受信処理の二経路から、別のイベントIDでOutboxへ追加されます。

途中で止まると「ユーザーはいるが、必要な権限や後続処理がそろわない」状態が残り得ます。再登録は既存ユーザーとして拒否される場合があり、足りない段階だけを補う保証にはなっていません。別IDで作られた同義イベントは、イベントID単位の重複防止でも一つにはなりません。

まず統合イベントの発行を明示的な登録サービス側へ一本化し、その後、登録成功に必要な初期データと後続処理の起動記録を同時確定する方向が妥当です。既存ユーザーから未完了部分を再開する方法も必要です。メールの実到達まで成功条件に含めるかは、別途決めます。根拠: [登録サービス][reg]、[初期化とイベント追加][reg-tail]、[もう一つの発行経路][reg-event]。

#### パスワード変更・リセット — 優先見直し

パスワード本体、イベント、期限、履歴追加、古い履歴削除は、複数の保存に分かれています。期限更新の保存結果を確認しない箇所があり、リセット経路も通常変更と同じ期限・履歴処理を通っていません。

パスワードだけ変わった後で失敗すると、利用者は旧パスワードで同じ変更を再試行できません。したがって、単なる要求の再送では期限・履歴の不足を補えないことがあります。

履歴・期限ポリシーを有効にする条件を確定し、必要な保存をまとめるか、不足状態を旧パスワードなしで補修できるようにする必要があります。保存結果を必ず検査することも基本条件です。根拠: [パスワード処理][password]、[期限更新][password-expiry]、[履歴処理][password-history]。

#### ロール割当・権限集合の置換 — 優先見直し

ロールの追加・削除や権限集合の置換では、複数回の保存があり、一部の保存結果を確認していません。途中失敗で、要求された集合とは異なる中間状態が残る可能性があります。

「管理者を最低一人残す」という事前確認も、異なるユーザーの管理者権限を同時に外す操作までは守れません。個別ユーザーの競合検査だけでは、管理者集合全体の条件を保護できないためです。

権限集合の更新を一まとまりにし、管理者数は集合全体を保護する制御が必要です。キャッシュへの反映失敗は別に回復できるようにします。根拠: [ロール割当][user-roles]、[権限更新][role-perms]。

#### グループ更新・メンバー追加 — 仕様次第

読んだ更新経路では、グループ属性とロール差分を一回で保存し、メンバー追加もまとめて保存しています。逐次実行では既存メンバーを除外します。

一方、同時編集で後からの内容を優先してよいか、同時追加の競合をどう返すか、保存後のキャッシュ無効化失敗をどう直すかは未確定です。集合全体の編集に競合検知が必要ならグループの版管理などを検討しますが、すべてのメンバー操作を確認済みとはしません。根拠: [グループ更新][group-update]、[メンバー追加][group-add]。

#### プロフィール・画像変更 — 改善推奨

古いプロフィールの更新を拒否する仕組みは、`If-Match`を付けた場合に利用できます。旧画像を最終保存後に削除する順序も、テナントテーマ変更より安全です。

ただし、画像アップロード、電話番号の更新、最終プロフィール保存は一つの保存ではありません。最終保存に失敗しても電話番号だけ先に変わる場合や、新しい画像だけ残る場合があります。

プロフィールとして一緒に変える項目の保存境界を整理し、孤立した新画像の回収や旧画像の削除を後から追えるようにすることが望まれます。専用の画像設定入口全体は詳細調査の対象外です。根拠: [プロフィール更新][profile]。

#### リフレッシュトークンとセッション更新 — 優先見直し

ユーザー側のトークン更新とセッション側のハッシュ更新が別々です。旧トークンが一致した場合だけ二つを同時に置き換える、という一つの更新境界にはなっていません。

並行した更新や途中失敗では、二つの正本候補が食い違い得ます。古いトークンを再送して同じ成功結果を取り出す契約も確認できません。

旧値を条件にした更新とセッション保存を一体化するか、更新操作を識別して結果を照会できる方式が必要です。ただし、セッションがない場合を許す既存の互換仕様があるため、これを壊さない判断が必要です。根拠: [更新ハンドラー][refresh]、[ユーザートークン保存][token-store]、[セッション更新][sessions]。

#### 二要素認証の有効化・無効化 — 優先見直し

設定保存の結果を確認せず成功を返す経路があります。無効化では、無効化と認証キーのリセットも別の保存です。

利用者には成功と表示されても、必要な設定が保存されていない可能性があります。保存結果の検査を必須とし、複数保存の途中失敗を一体として戻すか、明示的に補修できる状態として扱うべきです。有効化開始からの全経路を確認したわけではありません。根拠: [有効化の確定][twofactor-on]、[無効化][twofactor-off]。

#### ユーザーの無効化・削除 — 概ね妥当（同期状態更新の範囲）

読んだ共通サービスでは、自己無効化と管理者無効化を拒否し、保存結果も確認します。この経路に「二人の管理者を同時に無効化できる」という指摘を無条件で当てはめるのは不適切です。

同期的なユーザー状態の更新としては概ね妥当です。ただし、有効化と無効化を同時に行った場合の扱いや、その後の監査記録の保証までは別に確認が必要です。根拠: [状態変更サービス][status]。

#### 代理操作権限の終了・取消 — 改善推奨

DBの権限状態を終了・取消にした後で、判定用キャッシュを更新します。DB保存だけ成功すると、再実行は「すでに終了済み」として早期終了し、キャッシュを修復しない経路があります。

DBの状態は正しくても、判定への反映が遅れる可能性があります。終端状態への再要求でもキャッシュ同期をやり直すか、同期作業を耐久的に残す方向が適切です。どれだけの遅延を許すかによって優先度は上がります。代理操作開始時のトークン発行全体は今回の詳細範囲外です。根拠: [代理操作権限サービス][grant]。

### 5.2 入金・請求・契約（Billing）

#### 入金承認・請求支払・残高・台帳 — 優先見直し

支払処理では、請求書、入金申請、残高、台帳を一回で保存しています。同じ入金申請を二重計上しないための台帳の一意制約もあります。これは有効な保護です。

しかし、別々の二件の入金が同じ残高を読んで加算すると、台帳には両方残っても、残高は片方の計算結果で上書きされる可能性があります。例えば初期残高100に20と30を同時入金したとき、期待値150ではなく120または130になる形です。この数値は仕組みを説明する例で、再現試験の実測値ではありません。

また、承認状態の保存とOutbox追加が別で、承認済み申請を再承認しても欠けたイベントを補えません。残高単位の競合制御と再計算、同一操作の重複防止、承認とイベントの同時確定をそれぞれ設計すべきです。根拠: [支払と承認][billing-pay]、[残高計算][wallet]、[台帳の一意制約][ledger-unique]。

#### 月次利用量と請求データ — 優先見直し

期間別の利用量記録と請求書には重複を防ぐ制約があり、既存データを再利用します。しかし、指定された請求期間を利用量の取得先へ渡さず、現在の値を読む経路があります。

特にRedisの月次API回数を使い、前月の利用量記録がまだない場合、月初の前月請求で現在月のカウンタを読む可能性があります。前月キーは月境界で失効するため、後から前月値を取り直せる保証もありません。一度誤った期間記録が保存されると、再実行はそれを再利用するため、直るとは限りません。

測定APIに期間を明示し、請求根拠となる期間確定値を耐久的に残す必要があります。過去のプラン・単価や測定時点、丸め方も同じ文脈で決めます。これはOutboxや単なるリトライ追加では解決しない、値の正確性の問題です。根拠: [利用量取得][usage]、[月次ジョブ][monthly]、[Redisの期間キー][quota-period]。

#### 契約割当・契約イベントの受信 — 改善推奨

有効契約の取消と新規作成は一回で保存され、有効契約を高々一つにする制約があります。一方、その後の請求書作成やイベントの処理済み記録は同じ境界ではありません。

再配送で不要な契約置換を繰り返す可能性があるため、元イベントや論理操作を使った業務側の重複防止が必要です。契約変更と請求を同時に確定すべきか、イベントが逆順に来たら何を優先するかも確認します。根拠: [契約の置換・延長][subscription-maint]。

#### 請求書の発行・取消 — 仕様次第

状態遷移を確認して一回保存する構造です。ただし、支払と取消が同時に来た場合の優先順位や、発行成功に通知起動まで含めるかが明確でなければ、必要な追加制御を決められません。

通常の発行サービスには明示的なOutbox追加がありません。状態保存だけで目的を満たすなら、それだけを理由にOutboxを増やす必要はありません。通知が必須なら耐久的な起動記録を追加し、競合遷移を拒否したいなら期待状態や版を使った更新を検討します。根拠: [発行][invoice-issue]、[取消][invoice-void]。

### 5.3 テナント作成・期限・テーマ（Multitenancy）

#### テナントの初期構築 — 優先見直し

初期構築の記録と手順を保存し、ジョブを登録し、そのジョブIDを保存します。登録済みジョブの再実行では、完了済みの手順を飛ばす設計があります。

しかし、最初の記録保存後、ジョブ登録前に止まると、ジョブがないのに「待機中」の記録だけ残り得ます。開始・再試行の要求は進行中判定で拒否される場合があり、受け付けた仕事が自動では進まなくなります。また、自動再実行は同じ記録を使うのに対し、手動Retryは新しい記録を作るため、同じ意味の再開ではありません。

未登録の起動要求を後から発見して登録できる仕組みと、同一処理の再開・新規のやり直しを区別する設計が必要です。根拠: [初期構築サービス][provision]、[実行ジョブ][provision-job]。

#### 契約期限の延長 — 優先見直し

現在の有効期限を読み、月数を足して保存した後、キャッシュやイベントを更新します。

異なる延長要求が同じ期限を読むと、両方成功しても片方の延長が失われ得ます。反対に、同じ要求を再送すると新しい延長として二回足され得ます。取りこぼしと二重延長は、別々に防ぐ必要があります。

延長操作を識別し、テナント単位で直列化するか、競合時に再読込・再計算する制御が必要です。管理者が期限を直接補正する操作とは契約を分けます。根拠: [期限計算][renew]、[後続イベント][renew-event]。

#### 期限通知の定期走査 — 優先見直し

同じ期限について何度も通知しないため、通知済みの記録を保存してからOutboxへ追加します。

Outbox追加に失敗すると、通知記録だけ残ります。例外を記録してジョブは続くため、次の走査でも「通知済み」として飛ばされ、イベントが永久に起動しない経路があります。定期実行が存在するだけでは回復しません。

通知記録とOutboxを同時確定するか、「起動待ち」と「起動記録済み」を区別して次回走査で補修する必要があります。メールの実到達は、さらに別の保証です。根拠: [期限走査ジョブ][expiry-scan]。

#### テーマ画像の差し替え — 優先見直し

新しい画像をアップロードし、古い画像を消してからDBを保存します。

DB保存に失敗すると、参照は古い画像のままなのに、古い実体はすでにありません。DBだけリトライしても、消した画像の内容は戻りません。

まず新しい参照を保存し、古い実体の削除は後から追跡可能な作業として行う順序が適切です。DBに採用されなかった新画像の回収も必要です。根拠: [テーマ更新][theme]。

### 5.4 在庫・商品画像・カテゴリ（Catalog）

#### 在庫調整 — 優先見直し

在庫を読み、増減量を足して一回保存します。逐次処理では負在庫を拒否する検査があります。

ただし、同時に別の増減を行うと片方を取りこぼす可能性があり、同じ要求の再送は再び増減を適用します。「一回の保存」と「負値チェック」だけでは、この二つを防げません。

条件付きの原子的な増減更新、またはロック・競合検査後の再計算と、論理調整IDによる重複防止が必要です。根拠: [在庫更新][stock-handler]、[数量の検査][stock-domain]。

#### 商品画像の集合・代表画像・参照URL — 改善推奨

一つの商品内で代表画像を一つにする処理はありますが、DBの一意制約では守らない設計です。空の画像集合への同時追加などでは、集合全体の競合制御が必要です。

また、ファイル移動イベントによるURLの書き換えは、現在のURLが古い保存先に一致した場合だけ行います。順番どおりの重複には強い一方、イベントが逆順だと、最新の移動を飛ばして処理済みにし、古い移動だけ適用する可能性があります。

商品単位の版管理などで集合を保護し、URLはファイルIDや版を基に最新状態へ照合・修復できるようにする方向が適切です。根拠: [画像集合の処理][images]、[画像設定][image-config]、[URL更新の受信処理][image-consumer]。

#### カテゴリの親変更 — 改善推奨

親をたどって循環がないことを確認してから保存します。逐次の変更には有効です。

しかし、カテゴリAの親をBにする操作と、Bの親をAにする操作が同時に検査を通ると、保存後に循環する可能性があります。別々の行の版管理だけでも十分とは限りません。

階層全体の変更を適切に直列化するなど、複数行にまたがる条件を守る方式が必要です。作成・削除・復元時の参照整合性まで確認済みではありません。根拠: [親変更と祖先検査][category]。

### 5.5 チケット（Tickets）

#### 状態変更・コメント — 仕様次第

逐次の状態遷移を検査し、関連データを一回で保存します。すでに閉じたチケットへの再Closeのように、何もしない経路もあります。

ただし、同時編集や、閉鎖と別操作の競合をどこまで拒否するかは別です。コメントも新しい行として追加するため、要求再送時の重複をどこまで許すかを決める必要があります。

後勝ちの編集を許容するのか、期待した状態からのみ遷移させるのかを先に定義し、必要なら版管理やコメント操作IDを導入します。低影響の編集へ一律にOutboxを追加する必要はありません。削除・復元の個別経路は詳細調査外です。根拠: [状態遷移][ticket]、[コメント保存][ticket-comment]。

### 5.6 メッセージ・会話・既読（Chat）

#### メッセージ送信・削除・返信件数 — 優先見直し

メッセージと関連行、親の返信件数などを一回で保存し、その後にリアルタイム通知やメンションイベントを送ります。

削除を二回要求した場合、メッセージ自体の削除が二回目は何もしなくても、ハンドラーが親の返信件数を再び減らす経路があります。また、保存後の通知失敗はDB保存を戻さず、再送で別メッセージを作る可能性もあります。

親件数の変更は初回削除に限定し、競合した返信追加・削除でも正しい件数になる更新または再計算が必要です。画面のリアルタイム更新は再取得で補えるのか、メンション通知は必ず起動すべきかも分けて決めます。根拠: [送信][chat-send]、[削除][chat-delete]。

#### 二人会話・メンバー・リアクション — 改善推奨

二人会話の決定的な識別キーや、メンバー・リアクションの一意制約があります。そのため、重複行自体は抑えられます。

一方、同時に「なければ作成」を実行した片方が制約違反になった際、すでに作られた同じ会話のIDへ読み直して収束する処理はありません。データを守る制約と、利用者へ安定した結果を返すことは別です。

重複が確認できる競合だけを分類し、既存結果を返す改善が適切です。グループ会話は毎回作成する別仕様なので、二人会話と同じ重複排除を一律適用しません。根拠: [会話の検索・作成][dm]、[会話の一意制約][channel-config]。

#### 既読位置 — 改善推奨

指定メッセージが同じ会話に属するかは確認しますが、既読位置は無条件で代入します。

新しいメッセージまで読んだ要求の後に古い要求が届くと、既読位置が戻る可能性があります。「既読は通常、前にだけ進める」という要件なら、現在値と比較して進める更新が必要です。意図的に未読へ戻す機能は別操作として定義すべきです。根拠: [既読更新][chat-read]。

### 5.7 アップロード・移動・削除（Files）

#### アップロード確定と容量計上 — 優先見直し

アップロード確定では、保留状態を確認し、外部実体のサイズ・型などを検査して、容量を計上し、DB保存、Outbox追加へ進みます。実体を確認する検査はありますが、最初の容量確認は予約ではありません。

容量計上後にDB保存が失敗すると、容量だけ増えます。同時確定を一件に限定する条件付き更新にもなっておらず、再実行で再計上する可能性があります。逆に、確定済み保存後のイベント追加に失敗すると、再送は確定済みとして拒否され、イベントを補えません。

確定状態の一回だけの遷移、容量計上の操作ID、DBと容量の照合、業務保存とOutboxの同時確定を組み合わせる必要があります。容量の問題はquota有効構成を条件とする評価です。根拠: [確定処理][finalize]。

#### 公開範囲変更・保存先の移動 — 改善推奨

この経路は、他の多くの発行元より進んでいます。PostgreSQLの行ロックと明示トランザクションを使い、保存先参照とOutboxを同時に確定します。新しい実体のコピーはその前、旧実体の削除はコミット後です。

ただし、コピー後にDB側が戻ると、新しい実体だけ残る可能性があります。旧実体の削除と、他モジュールのURL更新も別の保証です。二回の移動を表すイベントが逆順に届く場合、最新URLへ収束しない経路が残っています。

既存の参照・Outboxの原子性は維持しつつ、孤立コピーの回収、削除結果の確認、参照先の最新状態との照合を追加する方向です。行ロックの保証はPostgreSQL前提で、他providerは単一書き込み担当を想定する別条件です。専用DBの受信先問題も別途確認します。根拠: [移動の保存境界][relocate]、[旧実体削除][relocate-delete]。

#### 削除済み・未確定ファイルの清掃 — 優先見直し

外部実体の削除を試し、失敗を抑制してからDBの対象行を消し、容量を返します。

外部削除が失敗しても行が消えると、次の清掃では同じ保存先を見つけられず、実体が残る可能性があります。容量返却の失敗や並行ジョブの二重返却も問題です。また、候補選定後に復元・確定された行を、最後の削除時に状態や期限を再確認せず消す競合も考慮が必要です。

ジョブには再試行設定がありますが、内部で例外を抑制して正常終了した部分には働きません。削除完了まで対象キーと進捗を残し、対象の確保・状態再確認・一回だけの容量精算を設計する必要があります。不可逆な情報喪失を含むため、特に優先度が高い箇所です。根拠: [削除済み清掃][purge-deleted]、[未確定清掃][purge-orphan]。

#### 旧形式ファイルの保存先移行 — 概ね妥当（再走査の範囲）

各ファイルは移動サービスを使い、失敗件を数えて最後に例外を返します。次の実行では未移行のキーを探すため、成功済みを繰り返し移すのではなく、残りを再処理できます。

個別失敗を捕捉してもジョブ全体の成功に見せない点は、前述の清掃処理と異なります。登録済みジョブとPostgreSQLという前提の下で、再開性の根拠があります。

ただし、外部コピーの孤立や再試行上限後の監視まで保証済みではありません。成功・失敗が混在する実DB試験も未実施です。根拠: [旧キー移行ジョブ][legacy-job]。

### 5.8 外部へのWebhook配信（Webhooks）

#### 配送先への振り分け・HTTP送信 — 優先見直し

配送先ごとにジョブを登録し、そのジョブがHTTP送信後に試行履歴を保存します。登録済みジョブとHTTPクライアントの両方に再試行があります。

しかし、一部のジョブ登録が失敗しても振り分け処理が正常終了し、Inboxが完了する場合があります。この配送は、送信リトライ以前に起動しません。一方、受信側で処理済みなのに送信側の履歴保存に失敗すると、再送で外部効果が重複します。

さらに、ジョブの最大5実行とHTTPクライアントの最大4試行が重なり、条件次第ではpolicy上最大20回相当のHTTP試行になります。実際はタイムアウトなどで少なくなる場合があり、別ジョブの重複はさらに別です。

配送予定を耐久的に残し、一つの論理配送で安定したIDを使い、受信側の重複排除・結果照会・失敗後の再投入まで契約する必要があります。試行ごとのIDは変わる一方、元イベントIDは安定しているため、その使い分けが重要です。根拠: [配送先振り分け][fanout]、[送信ジョブ][dispatch]。

### 5.9 アプリ内通知・メール（Notifications）

#### メンション通知生成・既読化 — 改善推奨

通知を保存し、リアルタイム通知を送り、その後にイベントの処理済み記録が付く構造です。通知保存後に停止すると、再配送で別IDの通知が増える可能性があります。

元イベントと受信者の組み合わせで重複を防ぐか、通知効果と処理済み記録を同時に確定する方向が適切です。一方、未読だけを対象とする一括既読更新は再実行に強く、生成時の問題と分けて評価できます。根拠: [通知生成][mention]、[一括既読][notify-read]。

#### 請求・期限関連のメール — 仕様次第

現行の共通送信処理は、失敗を記録して抑制するbest-effortです。メール送信に失敗してもイベントは処理済みになり得ます。逆に送信後、処理済み記録前に停止すると、同じメールを再送する場合があります。

任意のお知らせなら欠損許容を明記する選択があります。必須通知なら、配送作業と失敗状態を保存し、再試行・上限後の対応・送信事業者への照会を設計する必要があります。「Inbox完了」を「メール到達」と呼ばないことが重要です。各メールprovider内部のpolicyは未確認です。根拠: [メール受信処理][invoice-mail]、[共通送信処理][mail-sender]。

### 5.10 監査・保持（Auditing）

#### 監査記録の生成・搬送・保存 — 仕様次第

監査をメモリ上のキューへ入れ、バックグラウンドでSQLへ保存し、失敗時は再試行後にファイルへ退避します。通常のキューには古い項目を捨てる設定があり、重要な区分では待機しますが、どちらもプロセス停止時の耐久受理ではありません。

複数テナントの一部だけ保存した後で失敗すると、同じIDを含む全体の再試行が、保存済みテナントの主キー重複で止まり、後続へ進めない可能性があります。また、DB保存前の変更検出は、業務変更が最終的にコミットされた証明とは限りません。退避ファイルの保存自体が失敗する場合もあります。

診断補助として使うのか、欠損不可の証跡として使うのかで評価が変わります。後者なら、耐久的な受理、重複を受け入れる保存処理、試行と成功の区別、退避ファイルの永続化と再投入が必要で、優先見直し相当になります。根拠: [メモリキュー][audit-channel]、[SQL保存][audit-sink]、[再試行と退避][audit-worker]、[変更検出][audit-interceptor]。

#### 監査記録の保持期限・削除 — 仕様次第

種類ごとの期限で小分けに削除し、同じ条件の再実行では削除済み行は対象になりません。テナント単位で失敗しても、次の定期実行で残りを拾える構造です。

ただし、保持期間、削除期限、削除を保留すべき記録、失敗テナントへの対応期限は別に合意が必要です。バックアップから復元したときの再出現も含め、削除SQLだけで保持契約全体が成立するわけではありません。根拠: [保持削除ジョブ][audit-retention]。

### 5.11 棚卸しのみで、評価を保留した機能

次の機能は、存在や入口の分類はしましたが、保存・競合・再実行・回復までを通した詳細評価は行っていません。問題が見つからなかったという意味ではなく、**安全とも不適合とも、まだ判定していない**範囲です。

| 機能 | 次に確認したいこと |
|---|---|
| 課金プランの作成・更新 | 金額・精度、既存契約への影響、同時編集。 |
| テナントの有効・無効切り替え | 初期構築状態との関係、競合、途中停止後の再開。 |
| ブランド・商品の基本CRUD、価格変更、復元 | 参照関係、復元時の一意制約、価格精度、編集競合。 |
| チャネルの作成・編集・アーカイブ・復元 | メンバーとの関係、同時編集、復元競合。 |
| ファイルの論理削除・復元 | 復元期限、参照中ファイル、清掃との競合。 |
| Webhook購読の作成・削除 | 入力検査、削除後に残る配送作業の扱い。 |

## 6. 改善の類型・修正単位・優先順位

第5章は「どの機能に何があるか」という縦の整理です。本章では「同じ種類の問題を、どの修正パターンで扱うか」という横の整理を加えます。**課題の類型、実装をまとめる単位、着手する優先順位は別の軸**です。同じ類型でも業務影響が違い、同じ機能でも複数の類型にまたがります。

<a id="remediation-types"></a>

### 6.1 課題と修正パターンの類型

以下は第4・5章の調査結果を対応付けたもので、新たに不具合を確認した一覧ではありません。「代表的な対象」は修正候補の所在を示し、その機能全体が同じ原因だけで説明できるという意味ではありません。仕様次第の機能は、必要保証を採用した場合の対策候補として含めています。

| 課題の型 | 共通する症状・原因 | 修正の基本形 | 代表的な対象 |
|---|---|---|---|
| 正しい期間・根拠の値を使っていない | 保存や再実行は成功するが、業務上は別の期間・時点の値になっている。 | 測定対象の期間・単位・時点を明示し、確定値を保存する。誤った既存値の照合・訂正も設計する。 | 月次利用量・請求（5.2）。 |
| 一緒に確定すべきDB更新が分かれている | 一連の保存の途中で止まり、中間状態が残る。 | 必要な更新集合を定義し、同じDB・接続で扱える範囲はトランザクションへまとめる。まとめられない部分は進捗と補修を設計する。 | 登録、パスワード、ロール・権限、プロフィール、token/session、二要素認証（5.1）、契約と請求（5.2）。 |
| 異なる操作の同時更新を取りこぼす | 同じ値を読んで別々に計算し、後の保存が前の結果を上書きする。 | 原子的な加算、ロック、または期待した旧値・版に一致した場合だけの更新と再計算を使う。 | 残高（5.2）、期限延長（5.3）、在庫（5.4）、返信件数（5.6）。 |
| 行をまたぐ集合・階層の条件を守れない | 個々の行の検査は通るが、全体では「管理者が残る」「代表画像は一つ」「循環しない」などの条件を破る。 | 守る対象を集合・階層単位で定め、その範囲で競合制御する。DB制約で表せる条件は制約も使う。 | 管理者ロール解除（5.1）、商品画像・カテゴリ（5.4）。グループ・チケットの編集競合は仕様確認から。 |
| 同じ論理操作が複数回の効果になる | 二経路で同義イベントを作る、再送を新操作とする、効果の後に処理済み記録を付ける。 | 二重の発行元は一本化する。再送には安定した操作IDと入力の対応を持たせ、業務効果と重複防止を同時に確定する。競合して既存結果がある場合は、その結果へ収束させる。 | 登録イベント（5.1）、入金・契約（5.2）、期限延長（5.3）、在庫（5.4）、返信削除・二人会話（5.6）、通知生成（5.9）、監査の再投入（5.10）。 |
| 必須の後続処理を起動する記録が欠ける | 本体保存後、Outbox追加やジョブ登録の前に止まる。再要求は「作成済み・処理中」として終わる。 | 業務変更と起動要求を耐久的にそろえる。Outboxなどの保存境界を整え、ジョブ登録漏れや未完了を再発見できるようにする。 | 登録（5.1）、入金承認（5.2）、初期構築・期限通知（5.3）、アップロード確定（5.7）、Webhookの振り分け（5.8）。メンション・メールは必須性の確認が先。 |
| DB外の処理と保存結果が食い違う | 外部処理だけ成功する、削除失敗後に対象情報を消す、DB確定前に旧実体を消す。 | 外部処理の前後に状態を残す。確定後の削除、完了までの対象情報保持、操作IDによる一回精算、照会・補償を使い分ける。 | プロフィール画像（5.1）、テーマ画像（5.3）、容量計上・ファイル移動・清掃（5.7）、Webhook（5.8）、必須メール（5.9）。 |
| 古い要求・イベントや反映漏れで派生状態がずれる | 既読が戻る、画像URLが古いまま、DB終端状態とキャッシュが一致しない。 | 版・順序・現在値による条件付き更新、正本との照合・再計算を使う。反映失敗を再実行して修復できるようにする。 | 代理操作権限のキャッシュ（5.1）、商品画像URL（5.4）、返信件数・既読（5.6）、ファイル移動後の参照（5.7）。 |
| 失敗を成功に見せる、再試行を生かせない | 保存結果を無視する、別種の例外を重複と扱う、個別失敗を抑制してジョブ全体を成功にする。 | 保存結果と例外を分類し、真の重複だけを既存結果として扱う。再試行すべき失敗は呼出元へ返すか、個別の失敗作業として耐久的に残す。 | パスワード・ロール・二要素認証（5.1）、Inbox（4章）、ファイル清掃（5.7）、Webhook振り分け（5.8）。メールの抑制は必須配送にする場合に見直す。 |
| 稼働構成によって作用先・排他が変わる | 正しいテナントIDでもDB接続先が違う。単一担当の前提が複数インスタンスで崩れる。 | 完全なテナント情報を受信処理の構築前に解決し、作用先を試験する。担当権の期限切れ後の確定権限と、受信側の重複防止を確認する。 | 専用DBのイベント受信、Outboxの担当権、API予約（4章）、provider依存のファイル移動（5.7）。 |
| 最終失敗・保持・訂正を運用へつなげられない | 再試行上限後の対応が未定、保持期限や削除条件が未合意、照会や再投入の手順が不明。 | 要対応状態、検出期限、担当者、同じ操作としての再開、訂正・削除・保持の契約を決める。 | Outboxの隔離（4章）、ファイル清掃・移行（5.7）、Webhook（5.8）、メール（5.9）、監査搬送・保持削除（5.10）。 |

重要なのは、**トランザクションは同時更新の取りこぼしや外部送信の重複を自動では解決せず、重複防止は未起動の仕事を作らず、リトライは間違った期間値を正しくしない**ことです。対策の名前だけを横展開せず、対応する失敗条件ごとに受入試験を持たせます。

ユーザー無効化の同期保存と旧形式ファイル移行の再走査は、今回の範囲では概ね妥当と評価した比較例です。同じモジュールに他の課題があることを理由に、これらまで一律の修正対象にはしません。また、5.11の棚卸しのみの機能は、類型への確定割当ではなく追加調査の対象です。

<a id="remediation-work-units"></a>

### 6.2 修正作業をどの単位に分けるか

同じ修正パターンを使えることと、同じ実装や一つの変更で直せることは別です。以下は作業の切り分け案であり、行の順番が実施順を表すものではありません。

| 作業のまとまり | 横断してそろえること | 個別に実装・検証すべきこと |
|---|---|---|
| 期間値・金額の正確性 | 期間、測定時点、精度、訂正の契約。 | 請求用の測定APIと確定値の保存。既存の誤った値をどう見つけて扱うか。 |
| 同期DB更新の保存境界 | 複数保存を一体にする判断と、保存失敗の扱い。 | Identity managerの内部保存、各DbContext・接続、登録・権限・token等で何を同時確定するか。各機能を別の修正として完結させる。 |
| 数値・集合の競合と重複防止 | 操作ID、競合検査、再計算、既存結果への収束という設計パターン。 | 残高・在庫・期限は計算規則が違う。管理者集合・カテゴリ階層も守る範囲が違うため、一律の汎用ロックで済ませない。 |
| 起動要求と受信側の一回効果 | Outbox参加条件、Inboxの例外分類、テナント解決などの共通基盤の契約。 | 発行元ごとの業務保存と起動記録、ジョブ登録漏れの回復、受信側ごとの業務重複防止。共通基盤の修正だけで完了扱いにしない。 |
| 外部効果の進捗・補償 | 結果不明、安定した操作識別、失敗後も対象情報を保持する方針。 | ファイルのコピー・削除、Redis容量精算、HTTP・メールは確認手段が違う。外部システムごとに照会・補償・再送を設計する。 |
| 派生状態の収束 | 正本、版・順序、反映期限、照合・再計算の方針。 | URL、既読、返信件数、キャッシュで正しさの条件が違う。各々に逆順・再送・欠落の試験を用意する。 |
| 最終失敗・保持の運用 | 状態名、照会、警告、再投入の責任と期限。 | 金額の訂正、Webhook再送、ファイル再清掃、監査の保持・再投入は権限と手順を個別に定義する。 |

共通基盤を変える場合は、利用元への影響を確認する独立した変更として扱います。`src\BuildingBlocks`は明示承認が必要な保護対象であり、この整理は変更の承認を意味しません。実装パターンやテストの考え方は再利用しても、モジュール間で相手の内部実装へ直接依存させないことが前提です。

### 6.3 一つの機能で組み合わせる対策と依存関係

対応の見通しを立てるときは、類型別の作業一覧に加えて、機能ごとの完成条件を置きます。特に、次の例は一種類の対策だけで閉じられません。

| 機能 | 主な対策の組み合わせ | 着手時に押さえる順序・完成条件 |
|---|---|---|
| ユーザー登録 | 発行元の一本化＋初期データと起動要求の保存境界＋未完了再開。 | 成功に必要な初期データを決め、二経路の発行を一本化してから保存境界を整える。各停止点で、登録が戻るか残りを再開できることまで確認する。 |
| 入金・残高・台帳 | 同一入金の重複防止＋異なる入金の競合制御＋承認とイベントの同時確定。 | 一意制約が既にあることを確認し、異なる入金を取りこぼさない修正と承認後の起動漏れ対策を区別する。同一入金再送・二件同時入金・保存間停止のすべてを受入条件にする。 |
| アップロード確定・清掃 | 状態遷移の一回性＋外部容量の一回精算・照合＋イベント起動＋削除情報の保持。 | DBと容量計上の正本・補修方法を先に決める。確定処理だけを直しても清掃の二重返却は残るため、確定・削除・復元が競合する試験までつなげる。 |
| Webhook配送 | 配送予定の耐久保存＋論理配送ID＋外部の重複排除・照会＋上限後の再投入。 | 受信先との識別・照会契約を先に決める。起動漏れを直す作業と送信結果不明を扱う作業を分け、両方が成立して初めて必須配送の回復条件を満たす。 |
| 監査証跡 | 必要な耐久受理＋重複を受け入れる保存＋成功・試行の区別＋退避・保持・再投入。 | 欠損不可かを先に決める。欠損不可なら、メモリキューだけを変更して終わらず、部分保存後の再投入と退避先の障害まで検証する。 |

専用DBを使う受信処理では、上の機能別試験に先立ち、正しいDBへ作用することを確認します。一方、請求期間の修正や同期的な在庫更新など、イベント受信に依存しない修正まで一律に待たせる必要はありません。

### 6.4 業務影響に基づく着手順

優先順位は、問題の数やコードの複雑さではなく、**業務への影響、発生条件、気付きにくさ、戻しにくさ**で考えます。例えば、例外として分かりやすく失敗する処理より、成功したように見えて金額が違う処理や、復旧に必要なキーを消す処理を重く見ます。以下はその考え方に基づく着手順で、発生確率の実測順位ではありません。

| 順序 | 取り組む内容 | 理由・判断の前提 |
|---|---|---|
| 最初に決める | 成功条件、欠損・重複許容、専用DBやquotaの利用構成を確認する。専用DBでのイベント受信先を優先再現する。 | 必要保証が違えば正しい方式も変わる。誤ったDBを使ったままの設計・試験を避ける。 |
| 第1群 | 請求期間の誤り、残高・在庫・期限の加算競合、権限集合・二要素認証の成功判定、ファイル清掃とテーマ画像の情報消失。 | 正本の値、権限、不可逆な削除に直接影響する。再送だけでは直せない場合が多い。 |
| 第2群 | 登録イベントの一本化と保存境界、初期構築の起動漏れ、期限通知、アップロード確定、Webhookの配送予定、Inboxの例外分類と業務重複防止。 | 受理後の仕事の消失と、再実行時の二重効果を防ぐ。 |
| 第3群 | 画像URLの順序収束、返信件数、既読位置、キャッシュ修復、最終失敗の照会・再投入・監視。 | 正本と派生状態のずれを解消し、障害後の運用を成立させる。 |
| 最後に標準化 | 受入試験で確かめた方式を、ルールとSkillsへ反映する。 | 未承認の業務仮説や未検証の実装例を、そのまま規約にしない。 |

同じ群の中の厳密な実施順は、採用する機能と構成によって調整します。例えば、quota無効の環境で容量精算だけを最優先にする理由はありません。一方、欠損不可の監査を要件にするなら、監査は後回しではなく上位へ移します。

修正同士の依存も別にあります。登録のOutboxを直すなら、先に二経路の発行を一本化し、その後に保存境界を揃える方が安全です。Outboxを直すだけで、期間値の誤り、同時加算、外部削除、監査欠損まで一括解決するわけではありません。

## 8. 実装判断の前に決めたい業務・運用要件

技術的な反例があることと、その機能にどこまでの対策を求めるかは分けて考える必要があります。特に次の条件は、コードだけで決められません。

| 決めること | 決めないままだと困ること |
|---|---|
| 成功応答に何を含めるか | 本体の保存だけか、初期権限・必須通知の起動までかで、保存境界が変わる。 |
| どの欠損・重複を許すか | 画面更新の通知と、請求・権限・外部取引・証跡を同じbest-effortにしてしまう。 |
| 同時編集をどこまで拒否するか | 後勝ちでよい編集と、加算・階層・管理者数のように取りこぼせない更新を区別できない。 |
| 課金根拠の時点・精度・訂正方法 | 現在の値を過去の請求へ流用したり、丸めや訂正の扱いが不統一になったりする。 |
| 重複判定をいつまで保持するか | 古い要求や隔離イベントの再投入で、記録の期限切れ後に二重反映する。 |
| 外部受信先と何を約束するか | 操作ID、同じIDで異なる内容、結果照会、配送順序の扱いが食い違う。 |
| 自動再試行を諦めた後に誰が何をするか | dead-letterやFailedが残るだけで、完了にも要対応にも進まない。 |
| 保持と削除をどこまで保証するか | 復旧に必要な記録を早く消す一方、削除すべき実体が残るなどの矛盾が生じる。 |

ログやメトリクスがあるだけでは運用保証になりません。「何時間止まったら誰に通知するか」「どの操作を同じIDで再開し、どれを新しい操作とするか」「手動補償や訂正を誰が承認するか」まで定義する必要があります。バックアップ・復元後の重複防止記録の整合も同じです。

## 9. 今後のSkillsへつなげる判断方法

今回の調査からルール化すべきなのは、「すべてにOutboxを付ける」といった一律の方式ではなく、**機能の必要保証を言葉にしてから方式を選ぶ手順**です。

### 実装前に、一つの機能について説明できるようにする

1. 何がそろえば成功・受理・完了なのか。正しい値の根拠と、破ってはいけない条件は何か。
2. 同じ操作の再送と、異なる操作の同時実行をどう見分けるか。
3. 一緒に保存するものと、外部へ出るものは何か。
4. 各停止点で何が残り、再起動後に何を見て再開するか。
5. 結果不明や再試行上限後を、誰がどう照会・補償・訂正するか。
6. どの試験に通れば必要保証を満たしたと判断するか。何は未確認のままか。

この説明を、機能名、要件、保存境界、操作識別、再試行・回復、運用、受入試験を持つ簡潔な「書き込み保証の契約」として残すと、Skillsが設計理由を示せます。

### 機能の性質ごとに、要求する対策を変える

| 機能の性質 | Skillsが導くべき判断 |
|---|---|
| 単一の状態保存で完結する | 一回の保存と制約で足りるか確認する。不要なOutboxや長い処理管理を追加しない。 |
| 金額・在庫・期間を加算する | 同じ操作を一回にする仕組みと、異なる加算を取りこぼさない仕組みを両方求める。 |
| 権限集合・画像集合・階層を守る | 個別の行だけでは守れない条件を明示し、その範囲で競合制御する。 |
| 成功後に必須の非同期作業がある | 業務保存と起動要求を耐久的にそろえ、未起動・未完了を後から発見できるようにする。 |
| イベント受信で業務データを作る | Inboxの存在だけで合格にせず、業務効果と重複防止記録の境界を確認する。 |
| 外部送信・外部ファイルを扱う | 外部成功後の結果不明、安定した操作ID、照会・補償を扱う。 |
| 清掃・不可逆削除を行う | 完了確認まで対象情報を保持し、状態再確認と一回だけの精算を求める。 |
| 期間値・キャッシュ・件数を扱う | 正本、測定時点、順序、照合・再計算、許容遅延を決める。 |

既存の機能追加・エンティティ追加・イベント追加・テスト作成Skillsには、それぞれ関係する判断工程を接続する案が考えられます。ただし、本調査ではSkillsやルールの変更は行っていません。重要な要件が未決なら利用者へ確認し、共有基盤の変更が必要でも承認なしで変更しない、という境界も維持します。
