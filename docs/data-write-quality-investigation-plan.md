# データ書き込み品質の調査・評価計画

- 作成日: 2026-10-15
- 対象リポジトリ: `HiroshiYoshino/dotnet-starter-kit`
- 文書の位置付け: 新規調査の計画案。個別機能の調査結果や、承認済みの実装ルールではない。
- 実施範囲: 本計画の作成。アプリケーションの修正、障害試験、Skillsの変更は本計画に基づく別作業とする。

## 1. 目的

アプリケーションの書き込み機能について、必要なデータ品質と実装が提供する保証を対応付け、機能ごとに実装を評価できるようにする。

調査では、正常終了する経路だけでなく、並行実行、重複要求、一時障害、結果不明、途中停止、再起動、再試行枯渇までを扱う。特に「リトライの実装が存在すること」と「安全に再実行され、必要な書き込みが完了すること」を区別する。

最終的には、調査で得た判断基準を共通ルールとSkillsの設計へ展開し、新しい書き込み機能の実装時に、必要保証の判断、方式選択、受入条件の設定まで誘導できる状態を目指す。

### 調査で答える問い

1. 機能の成功・受理・完了とは、どのデータと外部効果が成立した状態か。
2. 破ってはいけない業務不変条件と、許容できる遅延・欠損・上書きは何か。
3. 障害・競合・重複の際、実装はどこまで安全性と完了性を提供するか。
4. 保証外の状態を検出し、確認・再実行・補償・訂正できるか。
5. 必要保証と実装の差を、どの基準で評価し、どの方式へ改善するか。
6. その判断をSkillsと検証へ再利用するために、何を必須入力・出力にするか。

## 2. 調査対象と単位

### 2.1 対象

調査開始時にコミットSHAを固定し、ソース参照はそのコミットの行番号付きリンクで記録する。調査途中で対象コードが変わった場合は、別の基準点として扱い、評価を混在させない。

対象は業務データを書き込むAPI、サービス、イベントconsumer、バックグラウンドjob、保守・削除処理である。関連するDB設定、制約、middleware、再試行設定、ストレージ・キャッシュ・ジョブ基盤、既存テストも読み取り対象とする。

| モジュール | 書き込み機能の棚卸しで確認する領域 |
|---|---|
| Identity | 登録、プロフィール、パスワード、ロール・権限・グループ、token・session等 |
| Billing | 請求書、利用量snapshot、wallet・台帳、契約・プラン等 |
| Multitenancy | テナント作成、provisioning、期限・プラン変更、テーマ等 |
| Catalog | 商品、在庫、画像集合、カテゴリ階層、削除・復元等 |
| Tickets | 担当・状態遷移、コメント、削除・復元等 |
| Chat | channel・membership、メッセージ・返信・reaction、既読等 |
| Files | アップロード、finalize、公開範囲、移動、削除・復元・purge等 |
| Webhooks | subscription、fan-out、HTTP配信、配信履歴等 |
| Notifications | 通知生成、既読化等 |
| Auditing | 監査生成、搬送、保存、再処理、保持・削除等 |

この表は棚卸しの出発点であり、件数や調査済み範囲を表さない。読み取り専用のAPIは、書き込み結果・状態照会・派生値の確認に関係する場合に扱う。

### 2.2 調査単位

主単位は、利用者またはシステムが一つの目的として実行する「書き込みユースケース」とする。endpointや `SaveChangesAsync` の数だけで機能を数えない。

各ユースケースに機能IDを付け、同期要求、内部サービス、job、consumer、結果照会までの経路を関連付ける。同じhandlerでも設定・tenant構成・呼び出し元により保証が変わる場合は、条件別に記録する。

全書き込み経路を先に棚卸しし、詳細調査の対象・対象外・未着手を明示する。代表例の調査結果を、未調査の機能に一般化しない。

### 2.3 作業上の境界

- 本番・共有環境への障害注入やデータ変更は行わず、動的検証は隔離したテスト環境を使う。
- `src\BuildingBlocks` は読み取り対象とするが、修正は別途明示的な承認を必要とする。
- 既存の未コミット変更を保持し、対象コミットとの差分が検証に影響する場合は記録する。
- 秘密情報や実利用者のデータを証拠・テストfixtureに含めない。
- 具体的なコード修正、migration、運用設定変更は、調査結果と判断基準を確認した後の別工程とする。

## 3. 保証の定義

| 区分 | 調査上の意味 |
|---|---|
| 安全性 | 重複反映、取りこぼし、部分更新、業務不変条件の破壊など、不正な状態を作らないこと。 |
| 完了性 | 受理した処理が、明示した障害条件・期間の下で、完了または明示的な失敗・要対応状態に到達すること。 |
| 結果の確認可能性 | 未実行・処理中・成功・失敗・結果不明を、利用者や運用者が区別できること。 |
| データの正確性 | 制約上有効なだけでなく、正本・測定時点・単位・業務計算に照らして値が正しいこと。 |

「APIが成功した」「DBに書けた」「非同期処理を受理した」「外部システムが処理した」は別の状態として扱う。機能ごとに成功応答の意味を定義し、保証の開始点と終了点を明示する。

有限回のリトライは、永久障害時の完了を保証しない。保証は「前提条件」「対象障害」「自動再試行の範囲」「期限」「枯渇後の処置」を含めて記述する。

また、リトライ回数、Inbox、冪等性filter、明示トランザクション等の存在だけを、機能全体の保証の証拠にしない。

## 4. 品質観点と調査項目

| 観点 | 調査する内容 | 主な確認対象 |
|---|---|---|
| 正本・正確性 | 正しい値の根拠、計算・集計方法、測定時点、元データとの照合可能性 | domain、集計処理、台帳、snapshot、外部入力 |
| 値の妥当性 | 必須項目、範囲、通貨・単位、精度・丸め、UTC、overflow、入力正規化 | validator、domain、型、DB制約 |
| 原子性・完全性 | 一緒に成功すべき更新集合、複数保存・DbContext・接続・DBの境界、部分成功 | handler、内部保存、transaction、接続共有 |
| 同時更新 | 読み取り後更新、lost update、競合検知、lock、分離レベル、競合後の再計算 | 更新SQL、version、実行順序 |
| 業務不変条件・参照整合性 | 一意性、関連行、状態遷移、階層・集合の条件、soft-delete・復元との関係 | unique・FK・check制約、domain、query filter |
| 冪等性・識別性 | 論理操作ID、重複判定の範囲・保持期間、同じキーで異なる入力、並行重複 | API、操作記録、Inbox、DB制約 |
| 順序・鮮度 | 古い要求・eventの反映、単調に進む値、逆順配送、再送と新操作の区別 | timestamp、version、event順序、更新条件 |
| リトライ | 実行主体、再実行単位、対象失敗、回数・間隔・総時間、結果不明、増幅 | client、EF、HTTP client、job、Outbox |
| 耐久的な起動・回復 | 受理記録、入力・進捗の永続化、enqueue前後の停止、restart後の発見 | job store、Outbox、処理状態、lease |
| DB外の効果・補償 | DBと外部の食い違い、重複送信、外部成功後の記録失敗、孤立object | Redis、ストレージ、HTTP、メール、job |
| 派生値・最終的整合性 | キャッシュ・カウンタと正本の差、許容遅延、再取得・再計算・照合 | cache、quota、件数、SignalR |
| 追跡・監査・訂正 | 操作・元eventとの関連、変更主体、成功と試行の区別、取消・訂正履歴 | 操作ID、監査、台帳、相関情報 |
| 耐久性・保持・削除 | 成功したデータの保持、清掃、復元、backup、重複防止期限との整合 | purge、保持設定、運用手順 |
| 分離・構成依存 | tenant・所有者、共有／専用DB、複数インスタンス、provider・設定差 | query filter、接続先、登録・設定 |
| 検出・運用 | 未完了、dead-letter、孤立、照合差分の検出、通知、再投入、対応責任 | metrics、log、状態照会、運用手順 |

各観点は、機能ごとに「必要保証」「実装の保証」「保証外」「証拠」を分けて記録する。該当しない項目には理由を付け、未確認の項目を非該当に置き換えない。

## 5. リトライ・再実行の詳細調査

### 5.1 再実行経路の一覧化

client、API、DB provider、外部HTTP client、job、event配送、手動再投入など、再実行し得る層をすべて列挙する。

各層について、次の形式で整理する。

| 項目 | 記録する内容 |
|---|---|
| 主体・起動条件 | 誰が何を検知して再実行するか。利用者の再送と自動再試行を区別する。 |
| 再実行単位 | SQL、保存、トランザクション全体、handler、job、機能全体のどれか。 |
| 対象失敗 | 接続障害、deadlock、serialization failure、競合、timeout、恒久エラー等。 |
| policyの実効値 | 有効化条件、環境差、回数、間隔・jitter、総時間、timeout、上限。既定値と実設定を区別する。 |
| 再実行時の入力・状態 | 入力や操作IDを保持するか。最新状態を再読込し、計算・検査をやり直すか。 |
| 重複防止 | 業務効果と重複防止記録を同時に確定できるか。保持期限や障害時のfail-openをどう扱うか。 |
| 並行実行・lease | 複数worker、lease失効、古いworkerの継続に対する所有権確認やfencing等があるか。 |
| 途中停止 | restart後に入力・進捗・未完了を発見し、どの段階から再開するか。 |
| 枯渇後 | 失敗記録、dead-letter、通知、再投入、照合・補償、対応責任。 |
| 実効保証 | 何がどの条件で完了するか。重複や未完了が残る条件も書く。 |

複数層のリトライは、送信回数・処理時間が増幅する可能性を調べる。同じ業務効果を伴う処理を、独立した複数層で無条件に再実行していないか確認する。

### 5.2 障害時点ごとの追跡

各保存・外部効果の前後に停止点を置き、以下を追跡する。

1. 障害時点で確定済みのDBデータ・外部効果・処理記録。
2. 呼び出し元が観測する応答またはtimeout。
3. 再実行の起動元と、使用する操作ID・入力・進捗。
4. 再実行による重複、取りこぼし、状態遷移の破壊の有無。
5. 自動回復できない場合の検出・照会・補償・手動対応。

DB commit直後の応答喪失、外部受信成功後のtimeout、consumer保存後の処理済み記録失敗は、「未実行」と決めつけず結果不明として扱う。

## 6. 必要保証と実装方式の判断基準

業務条件から必要保証を導く。既存実装の容易さを理由に必要保証を引き下げず、機能の性質に関係なく一律で高コストな方式を要求することも避ける。

| 機能の条件 | 必要保証・方式の候補 |
|---|---|
| 複数DB更新がそろって成功になる | 保存の集約、同一トランザクション、各保存結果の確認。 |
| 残高・在庫・期間などを加減算する | 原子的更新、行ロック、競合検知＋再読込・再計算。 |
| 同じ対象を複数利用者が編集する | 上書き許容の明示。許容しなければversion／ETag等。 |
| 重複要求が重複した業務効果を起こす | 安定した操作IDと、業務効果に結び付いた耐久的な重複防止。 |
| 成功後に必須の非同期処理がある | 起動要求の耐久化、未完了検出、完了／失敗状態、再投入。 |
| DBと外部システムをまたぐ | 原子性の境界を明示し、進捗・冪等化・補償・照合を設計。 |
| 集合・階層全体に不変条件がある | 集約や集合単位の競合制御、適切な分離レベル。 |
| 表示用・再計算可能な派生値である | 最終的整合性を選べるが、許容遅延と回復方法を明示。 |
| 欠損不可の会計・監査記録である | 耐久的な記録、追跡可能性、重複許容、成功と試行の区別。 |
| 処理失敗後に不可逆な効果が残る | 実行前の記録、外部の冪等性契約、照合・訂正・要手動対応の設計。 |

これは判断の出発点であり、特定の方式が必要保証を満たすかは実装・接続・設定・障害条件まで確認する。例えばトランザクションの存在だけではlost updateを否定せず、冪等性filterの存在だけではDB commit後の重複を否定しない。

業務要件が明文化されていない場合は、一般的な不変条件からの仮説を記録する。上書き、欠損、許容遅延、成功応答の意味など、複数の選択肢がある項目は確認事項として残し、実装上の挙動をそのまま承認済みの仕様とは扱わない。

## 7. 調査の進め方

| 段階 | 作業 | 完了時の成果 |
|---|---|---|
| 1. 基準点・環境の確定 | SHA、構成、DB provider、共有／専用DB、instance数、外部依存、有効設定、検証可能環境を記録する。 | 対象条件と制限事項。 |
| 2. 共通保証の調査 | 保存・接続・transaction、例外変換、API冪等性、DB／HTTP retry、job、Outbox／Inbox、tenant、監査の仕組みを読む。 | 共通保証一覧。適用条件と保証外を含む。 |
| 3. 全書き込み経路の棚卸し | endpoint、内部サービス、consumer、job、保守経路をユースケースに関連付ける。業務影響により詳細調査順を決める。 | 機能ID付き一覧、詳細調査対象、除外理由。 |
| 4. 必要保証・処理経路の分析 | 成功の意味、不変条件、保存・外部効果・再実行・状態照会を追跡する。制約・例外・保存結果も確認する。 | 機能別の保証契約、根拠、障害シナリオ、未決事項。 |
| 5. 重点検証 | 必要保証に直結する競合・重複・障害を、既存テストと隔離環境で確認する。 | 条件・期待値・実測結果・制限事項。 |
| 6. 評価・改善案の整理 | 必要保証との差、影響、修正方式、代替案、再検証条件を記録する。 | 評価表、優先順位、改善候補。 |
| 7. ルール・Skillsへの抽出 | 機能固有の判断と共通基準を分け、判断入力・出力・検証要求へ変換する。 | 共通ルール案、Skill仕様案、適用例。 |

段階4では、内部ライブラリやIdentityのmanager等が行う保存も含めて追跡する。ソース上の設定だけでなく、登録経路・有効化条件・実運用の前提まで確認する。

詳細調査は、金額・在庫・権限・不可逆削除・必須外部効果など、影響が大きい条件から着手する。これは調査順の決め方であり、調査前に個別機能を不適合と判定するものではない。

## 8. 検証シナリオと証拠

全機能に同じ試験を機械的に実施せず、必要保証と処理境界に対応したシナリオを選ぶ。

| シナリオ | 確認する結果 |
|---|---|
| 正常実行 | 成功の定義に含まれる行・関連行・外部効果が成立する。 |
| 最初の保存前／複数保存の間の失敗 | 不正な部分成功が残らない、または明示された回復状態になる。 |
| commit後の応答喪失・client再送 | 結果を確認でき、同じ論理操作の効果が二重反映されない。 |
| 同じ操作IDの並行要求 | 単一の業務効果に収束し、両要求の結果が説明できる。 |
| 同じキーで異なる入力／保持期限後の再送 | 拒否・新操作扱い・照会等、定義した挙動になる。 |
| 異なる操作による同一対象の並行更新 | 加減算を取りこぼさず、編集競合や集合条件を正しく扱う。 |
| 古い要求・eventの逆順到着 | 新状態や単調に進む値を不正に後退させない。 |
| 外部処理成功後の結果記録失敗 | 再実行時に重複を防ぐ、または検出・照合・補償できる。 |
| handler保存後の処理済み記録失敗 | 再配送で業務効果が二重化しない。 |
| 永続記録後のenqueue失敗／途中停止・restart | 未完了を発見し、必要な処理を再開できる。 |
| lease失効と旧workerの継続 | 並行・古い所有者による不正な確定を防ぐ。 |
| retry枯渇・恒久障害・キャンセル | 成功を装わず、失敗・要対応状態と回復手順が残る。 |
| cache・Redis・ストレージ等の停止 | 保証の劣化範囲が明示され、回復後に照合・修復できる。 |
| tenant・DB構成・複数instanceの差 | 対象外のデータを更新せず、宣言した構成条件で保証が成立する。 |
| 境界値・期間境界・削除／復元 | 精度、丸め、時刻、参照、保持・重複防止が仕様と一致する。 |

競合は別DbContext・別接続を使い、必要な箇所に同期点を置いて再現する。待ち時間に依存するだけの試験や、全呼び出しをmockにした試験を、DB競合・原子性の証拠にしない。

実DBが必要な制約・transaction・分離レベルの検証は、対象providerの隔離環境で行う。外部処理は、受信成功後の応答喪失や再起動を制御できるfixtureを使う。適切な環境や停止点を確保できない場合は、未検証理由と残る不確実性を明記する。

証拠は「要件・仕様」「実装・設定」「既存テスト」「今回の動的検証」に分けて記録する。テスト成功も、実施したシナリオ・構成の範囲で解釈し、あらゆる障害への保証に拡張しない。

## 9. 評価と修正優先順位

### 9.1 観点ごとの状態

各品質観点は、次の状態で記録する。

| 状態 | 意味 |
|---|---|
| 適合 | 明示した条件下で、必要保証に対応する実装根拠がある。証拠・未検証範囲も付ける。 |
| 不適合 | 必要保証を満たさない経路・条件が確認できる。 |
| 要件未決 | 必要保証を決める業務条件が未確定。 |
| 未確認 | 調査・検証が不足していて判断できない。 |
| 非該当 | その機能では対象効果や条件が存在しない。理由を記録する。 |

### 9.2 機能全体の評価

| 評価 | 判断基準 |
|---|---|
| 優先見直し | 必須の不変条件を破る、成功済みの必須処理を失う、不可逆な効果を重複させるなど、必要保証との重大な不一致がある。 |
| 改善推奨 | 主な制約は保てるが、競合時の結果、復旧、検出、retry枯渇後の対応等に不足がある。 |
| 仕様次第 | 許容する上書き・欠損・遅延等が未決で、必要保証を確定できない。 |
| 概ね妥当 | 必要保証と実装が対応し、保証外・構成条件・回復方法も明確。 |
| 判定保留 | 必要な証拠が足りない。未確認を「概ね妥当」に読み替えない。 |

機能評価は各観点の判断から導き、根拠となる不一致を機能ID・観点IDで示す。重大な不変条件違反を、他の観点の適合数や平均点で相殺しない。

### 9.3 修正優先順位

評価区分とは別に、以下をそれぞれ高・中・低・不明で整理し、優先理由を記述する。

- 業務影響: 金額、権限、不可逆削除、顧客への確定通知、法的・運用上の記録要求。
- 発生しやすさ: 通常の重複・並行要求で起こるか、特定の障害や構成が必要か。
- 検出の難しさ: 応答・監視・照合で発見できるか、正常な成功に見えてしまうか。
- 復旧の難しさ: 再計算・再実行で戻せるか、元情報が失われるか、外部への不可逆な効果があるか。

証拠の確かさとリスクは別に扱う。再現していないことを理由に影響を小さく見積もらず、仮説を確認済み事実として扱うこともしない。

## 10. 調査結果の整理形式

### 10.1 一覧

一覧は過度に横長にせず、次の3表に分け、機能IDで関連付ける。

| 表 | 主な列 |
|---|---|
| 対象・必要保証一覧 | 機能ID、module、入口、成功の意味、正本、不変条件、許容条件、調査状態。 |
| 実装・retry・復旧一覧 | 機能ID、保存境界、競合制御、再実行主体・単位、重複防止、耐久起動、枯渇後、保証条件、証拠。 |
| 評価・改善一覧 | 機能ID、観点、必要保証との差、影響、評価、優先理由、改善方式、受入条件、未決事項。 |

### 10.2 機能別の保証契約

機能ごとに、次の項目を簡潔に記録する。

- 機能ID・名称・入口・関連するjob／consumer。
- 必要保証の根拠: 明示仕様、合意事項、または未承認の業務仮説。
- 成功・受理・完了の定義、正本、必須不変条件、許容遅延・欠損・上書き。
- 操作IDと重複判定範囲、入力同一性、保持期限。
- 原子的に確定する範囲、競合制御、DB外の効果。
- retryの各層、対象失敗、再実行単位、実効設定、結果不明時の扱い。
- 永続入力・進捗、restart、lease、枯渇後、照合・補償・手動対応。
- 監視・状態照会、構成依存、保証外、未決事項。
- 対応するソース・設定・テスト・検証結果。

障害シナリオは「停止点→残る状態→再実行→到達結果→残るリスク」で記述する。単なるコード位置の列挙ではなく、なぜ必要保証を満たす／満たさないかを説明する。

## 11. 共通ルール・Skillsへの展開方針

調査結果から、業務条件に依存する判断と実装方式を分離して抽出する。現行実装の傾向を、そのまま正しい実装の基準にはしない。

| 展開先の案 | 内容 |
|---|---|
| `.agents\rules\data-quality.md` | 保証の用語、条件付きの必須基準、例外・未決事項・証拠の扱い。 |
| 書き込み設計用の新規Skill | 業務条件を入力し、必要保証、方式候補、選択理由、未決事項、受入条件を提示する。 |
| 既存Skillsへの接続 | `add-feature`、`add-entity`、`add-integration-event` 等の実装前工程に、保証判断を組み込む。 |
| テスト・レビュー・運用への接続 | 選択した保証に対応する競合・障害試験と、監視・回復手順を確認する。 |

Skillの基本手順は、業務条件の把握→必要保証の提示→未決事項の確認→方式選択→実装→保証に対応する検証とする。

Skillは少なくとも、保証契約、方式選択の理由、対象外の保証、必要な検証シナリオを出力する。低影響で単一保存のCRUDまで一律にOutbox・lease・大きなtransactionを要求せず、加減算・集合条件・外部効果等の条件に応じて必要な工程を追加する。

未決の成功条件・上書き許容・欠損許容等を、Skillが無断で低保証に決めない。既存helperの保証範囲が不足する場合は、不足を明示し、共有基盤の修正を自動的に実施しない。

基準案は、単一保存CRUD、編集競合、残高等の加減算、非同期処理、外部効果、削除・清掃など、性質の異なる機能に適用して確認する。判断のぶれ、過剰な対策、保証不足を修正してから共通ルールとして採用する。

Skillの記述だけで品質を保証したことにはしない。DB制約、実装、動的検証、監視・回復手順の対応付けが必要である。

## 12. 成果物と調査完了条件

### 成果物

- 対象コミット・環境・有効設定・調査制限の記録。
- 全書き込み経路の棚卸しと、詳細調査の対象・除外理由。
- 共通機構の保証一覧と適用条件。
- 機能別の保証契約、品質・retry・復旧・評価の一覧。
- 重点シナリオの検証結果と、未検証・要件未決の一覧。
- 改善候補、優先理由、受入条件。
- 共通ルールとSkillsの仕様案・適用例。

### 完了条件

- 棚卸しした書き込み経路が、調査対象または理由付きの対象外に分類されている。
- 詳細調査対象の各観点が、適合・不適合・要件未決・未確認・非該当のいずれかで記録されている。
- 機能ごとに成功の意味、操作ID、原子性、retry、結果不明、枯渇後・復旧が説明できる。
- 評価には必要保証の根拠と実装・設定の参照があり、仮説・確認済み事実・動的検証を区別している。
- 重点検証の結果が残り、実施不能な項目には理由・影響・追加確認方法がある。
- Skillsへ抽出する判断基準が、性質の異なる機能で検討され、過剰な対策と保証不足を避ける理由を説明できる。

調査の完了は、すべての機能が適合することや、未決・未検証がなくなることを意味しない。対象範囲と残る不確実性が明示され、次の判断・実装・検証へ進める情報がそろったことを意味する。
